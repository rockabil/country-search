# DESIGN

Архитектурные решения приложения **Country Search** — живого поиска стран через
[countries.dev](https://countries.dev).

Документ описывает четыре вещи, которые требует задание:

1. как устроена отмена устаревших запросов и почему именно так;
2. чем обоснована задержка debounce;
3. асимптотическая сложность ключевых функций;
4. какие принципы чистого кода применены и где конкретно.

---

## 1. Отмена устаревших запросов

### 1.1. Проблема

Пользователь печатает `spain` посимвольно. На каждый ввод уходит сетевой запрос.
Если ответ на ранний запрос (`sp`) придёт **позже**, чем ответ на поздний
(`spain`), экран перезапишется устаревшими данными — пользователь увидит
результаты для `sp`, хотя в поле уже `spain`. Это классическая гонка устаревших
ответов (stale response race).

Без явной отмены эта гонка — вопрос времени, а не «если»: достаточно одного
медленного ответа.

### 1.2. Решение: реальная отмена через `AbortController`

Предыдущий запрос **действительно отменяется** через `AbortController.abort()`,
а не просто игнорируется по флагу «актуальности». Это принципиально:

- **Сеть.** Отменённый запрос освобождает соединение и не тратит трафик.
  Игнорирование постфактум оставляет запрос «висеть» до ответа.
- **Наблюдаемость.** В DevTools → Network отменённый запрос помечается как
  `canceled`, это видно и проверяемо руками.
- **Требование задания.** Задание прямо запрещает маскировать гонку фильтрацией
  результатов постфактум («показывать только самый последний полученный ответ по
  таймстампу») — нужна именно отмена.

### 1.3. Где именно происходит отмена

Файл: `src/ui/searchController.ts`, функция `setQuery`.

Отмена выполняется **при каждом изменении ввода**, а не в момент, когда debounce
фактически запускает новый сетевой запрос:

```typescript
const setQuery = (query: string): void => {
  const trimmed = query.trim();
  lastQuery = trimmed;

  if (trimmed === '') {
    currentController?.abort();
    currentController = null;
    debouncedSearch.cancel();
    onStateChange({ kind: 'idle' });
    return;
  }


  currentController?.abort();
  currentController = null;

  onStateChange({ kind: 'loading', query: trimmed });
  debouncedSearch(trimmed);
};

## 2. Задержка debounce

### Выбранное значение: 300 мс  

debounceMs: 300 — значение по умолчанию в createSearchController. Обоснование:

- Ниже 150 мс — debounce почти не работает: при быстром наборе (5–6 символов
в секунду) запросы всё равно уходят на каждый символ, нагрузка на API и сеть
растёт без выигрыша в UX.  
- 150–300 мс - «золотая середина»: пауза между нажатиями у среднего
пользователя ~100–200 мс, поэтому 300 мс склеивает серию нажатий в один запрос, но не ощущается как задержка.  
- Выше 500 мс — пользователь замечает паузу между вводом и появлением 
результатов, интерфейс кажется «тормозным».
- 1000 мс и выше — приложение воспринимается как сломанное: пользователь
успевает усомниться, что запрос вообще ушёл.  
300 мс — компромисс между отзывчивостью и нагрузкой на сеть. В тестах значение переопределяется на 10 мс для скорости.

### Что будет, если убрать debounce

Каждый символ — отдельный сетевой запрос. При вводе spain уйдёт 5 запросов,
4 из которых будут отменены через AbortController. Сеть и API нагружаются впустую, на медленном соединении создаётся очередь запросов, задерживающая актуальный.

### Что будет, если сильно увеличить

Пользователь печатает spain, ждёт 1–2 секунды до появления результатов.
Субъективно — «приложение думает». Для живого поиска это неприемлемо: обратная
связь должна быть в пределах 300–500 мс.

### Реализация  

`src/core/debounce.ts` - обственная реализация (без lodash/подобных библиотек,
как требует задание). Сброс таймера при повторном вызове — через `clearTimeout` + новый `setTimeout`. Метод `cancel()` позволяет погасить отложенный вызов при  очистке поля или `dispose()`.  

## 3. Сложность алгоритмов (Big O)  

### mapCountryResponse — O(n)  

Файл: `src/core/mapCountryResponse.ts.`

```typescript
 export function mapCountryResponse(
  raw: ReadonlyArray<RawCountry>,
): CountryCard[] {
  return raw.map((country) => ({
    name: country.name,
    flagUrl: country.flags?.png ?? '',
    capital: country.capital ?? '',
    region: country.region,
    population: country.population ?? 0,
    languages: (country.languages ?? []).map((lang) => lang.name),
  }));
}
```

- #### Время: O(n),
  где n — количество стран в ответе. Один проход raw.map, для
каждой страны — константное число операций (чтение полей, опциональная
цепочка, ??, внутренний .map по языкам). Внутренний .map даёт O(m), где m — число языков одной страны (обычно 1–3, константа), поэтому общая сложность остаётся O(n).

- #### Память: O(n)  
  — новый массив CountryCard[] того же размера, что входной. Это неизбежно: функция чистая и не мутирует вход.

- #### Почему не быстрее:
  нельзя пропустить ни один элемент — нужно прочитать
каждую страну, чтобы построить карточку. O(n) — оптимум для этой задачи.

## 4. Принципы чистого кода

### 4.1. Разделение логики и DOM

Вся логика запроса/отмены/маппинга/дебаунса не зависит от DOM и тестируется без браузера и без реальной сети:
 
- `src/core/debounce.ts` - чистая функция высшего порядка, никакого DOM.
- `src/core/searchCountries.ts` - обёртка над fetch, принимает signal,
возвращает данные; сеть мокируется в тестах.
- `src/core/mapCountryResponse.ts` - чистая функция: вход → выход, без побочных
эффектов.
- `src/core/errors.ts` - `HttpError`, nолько хранение статуса и сообщения.
- `src/ui/searchController.ts `— состояния и оркестрация, без DOM; принимает `onStateChange` callback, поэтому тестируется с массивом состояний.

- `src/ui/render.ts` — единственное место, где строится DOM. Чистая функция `renderState(state, root)`: вход → DOM-операции, тестируется в jsdom.

### 4.2. Никакого innerHTML для динамического контента

`src/ui/render.ts` строит DOM через `document.createElement` и `textContent`. Это исключает XSS: данные из API (названия стран, столицы) вставляются как текст, а не как HTML. Требование задания выполнено явно.  

### 4.3. Явные типы состояний (discriminated union)  

`src/ui/searchController.ts`:

```typescript
export type SearchState =
  | { kind: 'idle' }
  | { kind: 'loading'; query: string }
  | { kind: 'results'; query: string; countries: CountryCard[] }
  | { kind: 'empty'; query: string }
  | { kind: 'error'; query: string; message: string; retry: () => void };
```

`switch (state.kind)` в `renderState` исчерпывающий: если добавить новое состояние, TypeScript потребует его обработать. Ошибка ловится на этапе компиляции, а не в рантайме.

### 4.4. Инъекция зависимостей

`createSearchController({ search, onStateChange, debounceMs })` принимает `search` параметром, а не импортирует `searchCountries` напрямую. Это позволяет в тестах подставить мок, а в проде — реальную функцию. Тот же приём — в
`renderState` (принимает root).

### 4.5. Единственная ответственность

- `debounce` — только задержка вызова.

- `searchCountries` — только сеть и проверка статусов.

- `mapCountryResponse` — только маппинг.

- `HttpError` — только хранение статуса и сообщения.

- `createSearchController` — только оркестрация состояний и отмены.

- `renderState` — только построение DOM.

Каждый модуль тестируется изолированно.

### 4.6. Явная обработка ошибок

`src/core/errors.ts` — `HttpError` extends `Error`с полем `status`. В
`searchCountries`:

```typescript

if (response.status === 404) return [];                       // не ошибка
if (!response.ok) throw new HttpError(response.status, ...);  // ошибка
// 
```

404 обрабатывается до !response.ok, потому что семантика API: 404 = «нет
совпадений». Это явно и читаемо.

### 4.7. Константы вместо магических чисел

`src/core/searchCountries.ts:`

```typescript
export const DEFAULT_TIMEOUT_MS = 5000;
```

Таймаут — именованная константа, а не 5000 в теле функции. Легко найти и
изменить.

### 4.8. readonly для входа

`mapCountryResponse(raw: ReadonlyArray<RawCountry>)` — функция не мутирует вход,
и тип это документирует. `CountryCard.languages: string[]` — новый массив, созданный функцией; входной RawCountry.languages не трогается.
